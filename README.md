# Auto MPG - Automated ML Pipeline (CI for ML)

A GitHub Actions pipeline that automatically validates data, trains a model,
evaluates it against a baseline with a quality gate, runs application tests,
and publishes a downloadable model package **only if every check passes**.

## Setup instructions

```bash
git clone <this-repo-url>
cd <this-repo>
pip install -r requirements.txt

# Run the pipeline locally, in this order (same order the workflow uses):
python src/data.py      # download + validate the dataset
python src/train.py     # train baseline + candidate, check quality gate, save model
pytest tests/ -v         # run application tests against the freshly trained model
```

The trained model and metrics report are written to `models/` (git-ignored;
regenerated by every run, both locally and in CI).

## Dataset

- **Source**: [Auto MPG](https://archive.ics.uci.edu/dataset/9/auto+mpg) (Quinlan, 1993; UCI
  Machine Learning Repository), via the commonly-used "seaborn-data" mirror.
  Included directly in this repository at `data/mpg.csv` (~21 KB, well under
  the 5 MB limit), so the pipeline has no dependency on an external site
  being reachable at run time.
- **Prediction task**: regression. 398 cars from 1970-1982.
- **Target variable**: `mpg` (miles per gallon, continuous).
- **Input features**: `cylinders`, `displacement`, `horsepower`, `weight`,
  `acceleration`, `model_year` (numeric), and `origin` (categorical: usa/europe/japan).
  The `name` column (car name) is dropped - it's a near-unique free-text identifier,
  not a predictive feature.
- **Missing values**: `horsepower` has 6 missing values out of 398 rows; these are
  imputed with the median (fit on the training split only) as part of the model
  pipeline. This is a real, intentional feature of the dataset - not something
  filtered out - to exercise realistic preprocessing.

## Model and evaluation

- **Baseline**: `DummyRegressor(strategy="mean")` - always predicts the mean
  training-set mpg.
- **Candidate model**: `RandomForestRegressor` (200 trees) inside a
  `scikit-learn` `Pipeline` with a `ColumnTransformer` that median-imputes
  numeric features and one-hot-encodes `origin`. Trains in well under a
  second on CPU.
- **Split**: single `train_test_split`, `test_size=0.2`, `random_state=42`
  (reproducible). All preprocessing (the imputer, the one-hot encoder) is
  `fit` only on the training split and applied to the validation split -
  never fit on validation data.
- **Metric**: **MAE** (Mean Absolute Error), in mpg. Lower is better.

### Why MAE?

MAE suits this task because:
1. It's in the same units as the target (mpg), so a result like "the model is
   off by 1.6 mpg on average" is directly interpretable to a non-technical
   reader, unlike R² or a squared-error metric.
2. It weights all errors linearly, which is appropriate here - there's no
   strong reason a 5-mpg miss on one car should be penalized non-linearly
   more than a 5-mpg miss on another (unlike RMSE, which would disproportionately
   punish a few large misses).
3. It's robust to the handful of high-mpg outlier cars in the dataset, which
   would otherwise dominate a squared-error metric.

### Quality gate and margin

Rule used (error metric, lower is better):
```
model MAE <= baseline MAE - margin
```
**Margin: 1.0 mpg.**

Why 1.0 mpg: the target ranges roughly 9-46 mpg with a standard deviation of
about 7.8 mpg. A 1.0 mpg margin is:
- **Large enough to be meaningful**: it rules out models that only marginally
  edge out "always guess the average" through noise or a lucky split - 1 mpg
  is a difference a car buyer would actually notice.
- **Small enough to be achievable** by a genuinely useful model without being
  an arbitrary near-zero threshold that any model would pass by chance.

What would happen if it were:
- **Too low** (e.g., 0.01 mpg): the gate would pass almost any model that
  is even trivially better than the baseline, including models barely
  distinguishable from "guess the mean" - defeating the purpose of a quality
  gate.
- **Too high** (e.g., 5 mpg, close to one full standard deviation): almost no
  realistic model would pass, since it would require near-perfect prediction
  from a handful of physical features - the gate would be unpassable and
  block legitimate, useful improvements from ever being published.

The metric (MAE), split (`random_state=42`, `test_size=0.2`), and margin
(1.0 mpg) are unchanged across the baseline run and both failure demonstrations
below.

## Validation and application tests

The pipeline fails (non-zero exit, no package published) if:
1. **Any required feature or the target column is missing**, or the target
   contains nulls - checked in `src/data.py::validate_columns`, which calls
   `sys.exit(1)`.
2. **The candidate model fails the quality gate** - checked in `src/train.py`,
   which calls `sys.exit(1)` if `candidate_mae > baseline_mae - margin`.
3. **Any application test fails** - `pytest` itself returns a non-zero exit
   code when a test fails, which stops the GitHub Actions job (no
   `continue-on-error` is used anywhere in the workflow).

Automated tests (`tests/test_pipeline.py`), which run against the model the
same job just trained:
- `test_saved_model_can_be_loaded` - the saved `.joblib` file loads and
  exposes `.predict`.
- `test_valid_sample_produces_expected_shape_and_type` /
  `test_multiple_valid_samples_produce_matching_row_count` - a valid input
  produces a `numpy.ndarray` of floats with one prediction per input row.
- `test_missing_required_feature_is_rejected` /
  `test_missing_feature_error_names_the_column` - an input missing a required
  feature raises a `ValueError` naming the missing column, instead of
  silently producing a (wrong) prediction.

## Pipeline / workflow

Workflow file: [`.github/workflows/ml-pipeline.yml`](.github/workflows/ml-pipeline.yml)
Trigger: push to `main`.

Single job, so training and testing share the same filesystem and can find
the just-trained model:
1. Check out repository
2. Set up Python 3.11
3. Install dependencies (`pip install -r requirements.txt`)
4. Load and validate the dataset (`python src/data.py`)
5. Train baseline + candidate model, evaluate the quality gate (`python src/train.py`)
6. Run application tests (`pytest tests/ -v`)
7. Build the model package (copy model, metrics report, prediction script,
   `requirements.txt` into `package/`, tagged with the run number and commit SHA)
8. Publish the package as a downloadable GitHub Actions artifact
   (`actions/upload-artifact`) - only reached if every prior step succeeded,
   since no step uses `continue-on-error` and the upload step has no
   `if: always()`.

### What caused each failed run?

**Failure A - model quality gate.** I set `N_ESTIMATORS = 1`, `MAX_DEPTH = 1`,
and `TRAIN_SUBSET_FRACTION = 0.03` in `src/train.py` (training on ~3% of the
training data with a single, very shallow tree). This drove the candidate's
MAE up to roughly the baseline's level, so `candidate_mae <= baseline_mae -
margin` was false. The quality-gate check in `src/train.py` called
`sys.exit(1)`, which stopped the job before the test or packaging steps ran -
**no model package was published.**

**Failure B - application test.** I disabled the missing-feature check in
`src/predict.py::predict_from_dataframe` (commented out the validation
`raise`). With that check gone, a request missing the `weight` column no
longer raised a clear `ValueError` - it instead reached `model.predict(...)`
and failed with a low-level, unhelpful `KeyError` from inside pandas/sklearn.
`test_missing_required_feature_is_rejected` and
`test_missing_feature_error_names_the_column` correctly failed as a result.
`pytest` exited non-zero, which stopped the job before the packaging step
ran - **no model package was published.**

**Recovery.** I reverted both changes (restored the original `N_ESTIMATORS`
/ `MAX_DEPTH` / `TRAIN_SUBSET_FRACTION` values, and restored the
missing-feature `raise` in `predict.py`) without weakening the gate's margin
or removing any test, then pushed again. All steps passed and the package was
published.

### Which checks demonstrate continuous integration and artifact delivery?

- **Continuous integration**: the workflow triggers automatically on every
  push to `main` and re-runs data validation, training, the quality gate,
  and the full test suite from a clean environment every time - no manual
  intervention, no reliance on my local machine or notebook state.
- **Artifact delivery**: the model package (trained model + fitted
  preprocessing, metrics report, prediction script, dependency file) is only
  built and uploaded as a downloadable GitHub Actions artifact when every
  preceding check succeeds, and it is uniquely identified by the workflow run
  number and commit SHA - giving traceable, gated delivery of a validated
  package on every successful run.

### MLOps maturity level

This implementation sits at **MLOps Level 1 (ML pipeline automation)** in
Google's maturity model, not Level 0 (manual process) and not yet Level 2
(full CI/CD with automated pipeline deployment and monitoring).

**Why Level 1, not Level 0:** the pipeline is not a one-off, manually run
notebook. Data validation, training, evaluation against a baseline, testing,
and packaging are all defined as code, run automatically on every push, and
are reproducible (fixed random seed and split) - which is the core Level-1
capability of an automated, repeatable training pipeline with a quality gate.

**Why not Level 2:** there is no automated *deployment* of the package (no
live endpoint, container build, or rollout - this is explicitly out of scope
per the assignment), no automated trigger for retraining based on new data or
drift, no model/data versioning system beyond git + the run-numbered
artifact, and no monitoring of a deployed model's real-world performance.

**What remains to reach Level 2**: add a CD stage that automatically builds
and deploys the published package (e.g., to a container registry or serving
endpoint) after the artifact passes, introduce a model/experiment registry
instead of ad hoc artifacts, add scheduled or data-triggered retraining, and
add production monitoring that feeds performance data back into future
training runs.
